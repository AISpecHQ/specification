# AISpec — RESUME

Version: 0.1
Status: Pre-production — Specification Phase
License: Apache License 2.0

## Overview

AISpec is an open, vendor-neutral specification for versioning, describing, and managing AI systems.

Core premise: Just as Git became the universal standard for source code versioning, AISpec aims to become the universal standard for AI system versioning.

What AISpec provides:
- Universal language for AI system representation
- Framework-agnostic versioning
- Model-agnostic and provider-agnostic design
- Human-readable, portable, extensible specification

What AISpec is NOT:
- LLM provider
- AI framework
- Orchestration engine
- Workflow builder
- Deployment platform
- Replacement for Git

## Core Concepts

Project: Highest-level container; complete AI application
Repository: Persistent store of complete project history
Node: Smallest versionable unit (Agent, Prompt, Tool, Workflow, Memory, etc.)
Snapshot: Complete immutable state of a Node at a specific moment
Commit: Immutable record of transition from one Snapshot to another
Branch: Alternative evolution path for a Project
Merge: Combines two Branches into one
Diff: Deterministic difference between two Snapshots
Rollback: Restores previous Snapshot (creates new Commit)
Evaluation: Measurable results attached to a Snapshot
Flow: Describes how Nodes are connected (directional)
Edge: Directional connection between two Nodes
Environment: Deployment stage (Development, Testing, Staging, Production)
Release: Stable version promoted to an Environment
Tag: Human-readable label attached to a Commit
Capability: Describes what a Node can do (behavior, not implementation)
Tool: Concrete implementation of one or more Capabilities
Provider: Implementation responsible for a service (OpenAI, Anthropic, etc.)
Runtime: Execution environment
Connector: External dependency (Database, REST API, Storage, etc.)
Artifact: Resource generated by a Node (Prompt, Dataset, Document, etc.)
Policy: Operational constraints (cost limits, security rules, etc.)
Extension: Optional capability added without modifying core specification

Relationships: Project → Repository → Branch → Commit → Snapshot → Node → Evaluation / Artifact / Connector

Invariants:
- Project owns one Repository
- Repository contains one or more Branches
- Branch contains one or more Commits
- Commit references one or more Snapshots
- Snapshot belongs to exactly one Node
- History is immutable
- Every object has a globally unique identifier

## Design Principles

1. Open Standard — Publicly available; anyone may implement without permission
2. Vendor Agnostic — Independent of any AI provider, cloud, or framework
3. Framework Agnostic — Works with LangGraph, CrewAI, AutoGen, custom apps
4. Language Agnostic — Implementable from Python, TypeScript, Go, Rust, Java, C#
5. Version First — Every meaningful change is a new version
6. Immutable History — Published versions never modified
7. Human Readable — Understandable without proprietary tools
8. Machine Friendly — Deterministic and easy to parse
9. Portable — Move between environments with minimal changes
10. Extensible — Evolves through extensions, not breaking changes
11. Minimal Core — Only universally useful concepts in core
12. Explicit Over Implicit — Avoid hidden behavior
13. Observable — Every version explainable
14. Reproducible — Same specification → same system
15. Security by Design — Secrets referenced, not stored
16. Community Driven — Evolves through public RFCs

Guiding Question: Does this make AI systems easier to understand, version and reproduce?

## Specification (RFC Series)

RFC-0000: Core Philosophy — Design principles and guiding philosophy
RFC-0001: Repository Layout — Canonical directory structure
RFC-0002: Commit Format — Immutable change record structure
RFC-0003: Snapshot Format — Complete object state representation
RFC-0004: Branch Format — Independent development path structure
RFC-0005: Validation Rules — Repository integrity and consistency
RFC-0006: Graph Model — AI system structural representation
RFC-0007: Extension System — Optional capability architecture
RFC-0008: Versioning Strategy — Semantic Versioning policy
RFC-0009: Storage Engine — Logical persistence model
RFC-0010: SDK Compliance — Minimum SDK requirements

### RFC-0000 — Core Philosophy

Keywords: MUST, SHOULD, MAY, MUST NOT (RFC 2119)

Scope: Repository structure, versioning model, object model, graph representation, storage format, validation, compatibility

Non-scope: Model execution, prompt engineering, agent frameworks, LLM providers, infrastructure, user interfaces

### RFC-0001 — Repository Layout

Root Structure:
my-project/
├── aispec.yaml
├── nodes/
├── flows/
├── branches/
├── commits/
├── snapshots/
├── evaluations/
├── environments/
├── policies/
├── connectors/
├── artifacts/
├── extensions/
└── .aispec/

Rules:
- Reserved directories are case-sensitive
- Unknown directories must be ignored
- All objects should exist only once
- History must be append-only

### RFC-0002 — Commit Format

Structure:
id: c_8fd12ac93
parents: [c_a9213, c_45ff2]
branch: main
author: manuel
timestamp: 2026-08-02T14:25:16Z
message: Initial Commit
snapshotIds: [s_7812, s_9183]
tags: [stable, production]
metadata: {}

Rules:
- Immutable after creation
- First Commit has no parent
- Merge commits reference 2 or more parents

### RFC-0003 — Snapshot Format

Structure:
id: s_91ab82
nodeId: router-node
version: 17
createdAt: 2026-08-02T16:42:11Z
configuration:
  model: gpt-5
  temperature: 0.7
  timeout: 30s
capabilities:
  - text-generation
  - web-search
connectors: [PostgreSQL, Redis]
artifacts: [prompt_v3.yaml]
metadata: {}

Rules:
- Immutable after creation
- Belongs to exactly one Node
- May be referenced by many Commits
- Configuration must be syntactically valid

### RFC-0004 — Branch Format

Structure:
id: b_81a92
name: feature/router
parent: main
head: c_918ab
createdAt: 2026-08-02T18:14:03Z
author: manuel
description: Testing Claude Sonnet against GPT-5
tags: [experiment]
metadata: {}

Rules:
- Default branch: main
- Branches reference Commits (don't own them)
- Deleting a Branch does not delete Commits

### RFC-0005 — Validation Rules

Levels:
- Error: Invalidates repository; must reject
- Warning: Recommended improvement; no rejection
- Info: Implementation guidance

Core Validations:
- Repository: aispec.yaml; unique identifiers; valid references
- Commit: ID, timestamp, branch, valid Snapshots, valid parents
- Snapshot: ID, Node, version, timestamp, valid configuration
- Branch: ID, unique name, valid HEAD Commit
- Graph: Unique Nodes; valid Edges; no broken references

Process: Repository → Schema → Objects → References → Graph → Extensions

### RFC-0006 — Graph Model

Structure:
- Directed graph representing AI system structure
- Nodes = Entities (Agent, Tool, Prompt, Memory, etc.)
- Edges = Directional Relationships

Relationship Types: uses, depends-on, reads, writes, invokes, evaluates, routes-to, produces, consumes

Rules:
- Each Node has globally unique ID
- Nodes are immutable through Snapshots
- DAG recommended; cycles must be documented
- Graph reconstructed from Snapshots

Example:
Agent → Router → GPT-5
              → Claude
              → Memory → Database

### RFC-0007 — Extension System

Structure:
id: ext.memory.redis
name: Redis Memory Extension
namespace: org.aispec
version: 1.2.0
author: Manuel
description: Redis-based memory storage
entrypoint: redis_memory.so
requires:
  aispec: ">=1.0.0"
metadata: {}

Rules:
- Extensions must not modify core behavior
- Unknown extensions must be ignored
- Extension failures must not invalidate repository
- Namespaces prevent collisions

### RFC-0008 — Versioning Strategy

Format: MAJOR.MINOR.PATCH (Semantic Versioning)
- MAJOR: Breaking changes (rare)
- MINOR: New functionality (compatible)
- PATCH: Fixes (no behavior change)

Rules:
- Repository must declare AISpec version: aispec.version: 1.0.0
- Backward compatibility preferred
- Deprecated features supported for 1 or more major releases
- Extensions must declare supported AISpec version

### RFC-0009 — Storage Engine

Principles:
- Canonical storage = filesystem
- Objects stored as individual YAML files
- Repository reconstructable from files only
- Indexes and caches are optional and disposable

Rules:
- Logical object stored independently
- Must preserve object identifiers and relationships
- Compression must be transparent
- Integrity failures reported during validation

### RFC-0010 — SDK Compliance

Compliance Levels:
- Core: Read/write repositories
- Standard: Validation, graph navigation, manipulation
- Full: All RFCs + optional extensions

Required Operations:
- Repository: create, open, save, close, validate
- Commit: create, get, list
- Snapshot: create, get, list, compare
- Branch: create, merge, switch, delete, list
- Graph: getNode, getChildren, getParents, traverse
- Validation: validateRepository, validateObject

Rules:
- Must declare supported AISpec version
- Must preserve object integrity
- Unsupported extensions must be ignored
- Errors must be structured and machine-readable

## Architecture Layers

Applications → SDK → API → Engine → Repository

## Implementation Components

AISpec Engine:
Purpose: Reference execution layer
Responsibilities: Repository management, Commit/Snapshot creation, Branch management, Graph construction, Validation, Object indexing, Repository reconstruction
Not responsible for: Running AI models, Executing workflows, User interfaces, Cloud synchronization

AISpec SDK:
Purpose: Language-specific developer libraries
Official SDKs: Python (PyPI), TypeScript (npm), Go (Cargo), Rust (crates.io), Java (Maven), C# (NuGet), Swift (SwiftPM)
Responsibilities: Opening repositories, Creating Commits/Snapshots, Managing Branches, Navigating Graph, Validation, Serialization

AISpec Cloud:
Purpose: Hosted collaboration platform (optional)
Core Services: Repository Hosting, Synchronization, Team Collaboration, History Visualization, Graph Visualization, Search, Validation, Releases, Organization Management
Rules: Repositories must work offline, Cloud-specific features optional, No vendor lock-in

AISpec CLI:
Purpose: Standard terminal interface
Operations: Repository creation, Commits, Branching, Validation, Graph inspection

## Philosophy Summary

Simplicity: Minimal core; features belong in implementations
Stability: Breaking changes extremely rare
Portability: Independent of providers, languages, runtimes
Extensibility: Additive changes preferred
Human Readability: Reviewable without proprietary tools
Immutability: History append-only

Core Separation:
- AISpec describes systems
- AISpec does not execute systems
- Execution belongs to external runtimes
