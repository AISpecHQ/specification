# Domain

> **The Domain Model defines the fundamental concepts of AISpec.**

Every implementation of AISpec must use these concepts consistently.

This document intentionally defines concepts, not implementation details.

---

# Design Philosophy

AISpec models AI systems using a small number of universal building blocks.

The goal is to describe AI systems independently of any framework, provider or runtime.

Every AI system should be representable using these concepts.

---

# Project

A **Project** is the highest-level container.

It represents a complete AI application.

A project contains one or more Nodes.

Examples:

* Customer Support AI
* Sales Assistant
* Research Pipeline
* Autonomous Workflow

A Project owns:

* Nodes
* History
* Branches
* Metadata

---

# Node

A **Node** is the smallest versionable unit.

A Node represents a single logical component.

Examples:

* AI Agent
* Prompt
* Workflow
* Tool
* Memory
* Evaluation
* External Connector

Every Node has:

* unique identifier
* type
* metadata
* versions

Nodes never execute.

They only describe something that exists.

---

# Snapshot

A Snapshot is a complete description of a Node at a specific moment.

Snapshots are immutable.

A Snapshot contains the full state of a Node.

It is never a partial update.

---

# Commit

A Commit records the transition from one Snapshot to another.

Every Commit contains:

* ID
* timestamp
* author
* message
* parent commit
* affected snapshots

Commits never modify history.

They only append new history.

---

# Branch

A Branch represents an alternative evolution of a Project.

Branches allow experimentation without affecting production.

Every Branch maintains its own sequence of Commits.

---

# Merge

A Merge combines two Branches into one.

The specification defines the operation.

Implementations decide how conflicts are resolved.

---

# Diff

A Diff describes the difference between two Snapshots.

Diffs must be deterministic.

Two implementations comparing the same Snapshots should produce equivalent results.

---

# Rollback

Rollback restores a previous Snapshot.

Rollback never deletes history.

Instead, it creates a new Commit pointing to a previous state.

History remains complete.

---

# Evaluation

An Evaluation represents measurable results produced by a Snapshot.

Examples:

* latency
* cost
* accuracy
* benchmark score
* human rating
* task success rate

Evaluations are attached to Snapshots.

They are never attached directly to Projects.

---

# Connector

A Connector represents an external dependency.

Examples:

* Database
* REST API
* Storage
* Queue
* Email Provider
* Authentication Provider

AISpec describes Connectors.

It does not implement them.

---

# Provider

A Provider is the implementation responsible for a service.

Examples:

* AI Model Provider
* Storage Provider
* Memory Provider

Providers may change without changing the surrounding Project.

---

# Artifact

An Artifact is any resource generated by a Node.

Examples:

* Prompt
* Configuration
* Dataset
* Output
* Document
* Image
* Audio
* Video

Artifacts may be versioned independently.

---

# Metadata

Metadata stores descriptive information.

Examples:

* author
* tags
* labels
* creation date
* description

Metadata must never alter system behavior.

---

# State

State represents the current active Snapshot of a Node.

A Node may have many Snapshots.

Only one Snapshot can be active at a time within a Branch.

---

# Workspace

A Workspace is the editable environment where changes occur before becoming a Commit.

The Workspace is mutable.

Snapshots are immutable.

---

# Repository

A Repository stores the complete history of a Project.

It contains:

* Branches
* Commits
* Snapshots
* Metadata

A Repository is the persistent representation of an AISpec Project.

---

# Relationships

```text
Project
│
├── Repository
│
├── Branch
│
├── Commit
│
└── Node
     │
     ├── Snapshot
     │
     ├── Evaluation
     │
     ├── Artifact
     │
     └── Connector
```

---

# Invariants

The following rules must always be true.

* A Project owns one Repository.
* A Repository contains one or more Branches.
* A Branch contains one or more Commits.
* A Commit references one or more Snapshots.
* A Snapshot belongs to exactly one Node.
* Nodes are versioned through Snapshots.
* History is immutable.
* Rollback creates a new Commit.
* Every object has a globally unique identifier.

---

# Future Extensions

The Domain Model is intentionally minimal.

Future RFCs may introduce additional concepts without modifying the existing core model.

The core vocabulary should remain stable over time.

---

# Flow

A **Flow** describes how Nodes are connected.

While a Node defines *what* a component is, a Flow defines *how* components interact.

Flows are directional.

They describe the movement of information through a Project.

Examples:

* User → Router Agent → Sales Agent
* Vision Model → OCR → Validation → Database
* Research Agent → Planner → Writer → Reviewer

A Flow never stores business logic.

It only represents relationships.

---

# Edge

An **Edge** is a directional connection between two Nodes.

Every Flow is composed of one or more Edges.

An Edge defines:

* source Node
* target Node
* connection type
* optional metadata

AISpec does not dictate execution behavior.

It only describes topology.

---

# Environment

An **Environment** represents a deployment stage.

Typical environments include:

* Development
* Sandbox
* Testing
* Staging
* Production

A Snapshot may exist in multiple Environments.

Promotion between Environments must preserve history.

---

# Release

A **Release** is a stable version promoted to an Environment.

A Release references one or more Commits.

Releases are intended for deployment and reproducibility.

Example:

```text
v1.0.0
Production
Commit: c8fa21
```

---

# Tag

A **Tag** is a human-readable label attached to a Commit.

Examples:

* v1.0
* Stable
* Demo
* Customer Release
* Before Migration

Tags never modify history.

---

# Workspace Session

A Workspace Session represents temporary work before a Commit is created.

A session may contain:

* pending changes
* temporary files
* experiments
* local metadata

Workspace Sessions are intentionally ephemeral.

Only Commits become permanent history.

---

# Identity

Every AISpec object must have a globally unique identifier.

Identifiers never change during the lifetime of an object.

Human-readable names may change.

Identifiers may not.

---

# Reference

Objects reference one another using identifiers.

Objects should never duplicate information already owned by another object.

This keeps the specification normalized and extensible.

---

# Lifecycle

Every versionable object follows the same lifecycle.

```text
Create
   │
Edit
   │
Workspace
   │
Commit
   │
Snapshot
   │
Evaluation
   │
Release
   │
Archive
```

---

# Core Domain Summary

AISpec is built around the following vocabulary:

* Project
* Repository
* Branch
* Commit
* Snapshot
* Node
* Flow
* Edge
* Evaluation
* Connector
* Provider
* Artifact
* Workspace
* Environment
* Release
* Tag
* Metadata

These concepts form the immutable core of the specification.

Future versions should extend this vocabulary rather than replace it.

---

# Domain Design Goals

The Domain Model should satisfy the following requirements:

* Framework independent.
* Provider independent.
* Language independent.
* Runtime independent.
* Cloud independent.
* Human understandable.
* Machine readable.
* Backward compatible.
* Extensible without breaking existing implementations.

The Domain Model is considered the single source of truth for every future AISpec implementation.

---

# Capability

A **Capability** describes what a Node is able to do.

Capabilities define behavior.

They do not define implementation.

Examples:

* Text Generation
* Image Generation
* Audio Processing
* Video Understanding
* Web Search
* Code Execution
* Database Query
* Email Delivery
* File Processing
* Tool Calling
* Function Calling
* Memory Retrieval
* Planning
* Reasoning
* Classification
* Translation
* Summarization

A Capability remains stable even if the underlying implementation changes.

---

# Tool

A **Tool** is a concrete implementation of one or more Capabilities.

Examples:

Capability:

```text id="0hvx7z"
Database Query
```

Possible Tools:

* PostgreSQL
* MySQL
* MongoDB
* SQLite

---

Capability:

```text id="m9pqtr"
Email Delivery
```

Possible Tools:

* Gmail
* Microsoft Graph
* SendGrid
* Mailgun

AISpec versions Tool definitions.

AISpec does not execute them.

---

# Provider

A Provider supplies an implementation.

Examples:

Model Providers

* OpenAI
* Anthropic
* Google
* Local Runtime

Storage Providers

* S3
* Azure Blob
* Cloudflare R2

Database Providers

* PostgreSQL
* MongoDB
* Redis

Providers are interchangeable.

Capabilities remain constant.

---

# Runtime

A Runtime is the execution environment responsible for running AI systems.

Examples include:

* Local Runtime
* Cloud Runtime
* Container Runtime
* Edge Runtime

AISpec describes Runtime metadata.

Execution is outside the scope of the specification.

---

# Configuration

Configuration represents the operational parameters of a Node.

Examples include:

* model parameters
* timeout
* retry policy
* temperature
* token limits
* memory settings

Configuration is versioned.

Configuration changes create new Snapshots.

---

# Secret Reference

AISpec never stores secrets.

Instead, it references them.

Examples:

* API keys
* Database passwords
* OAuth credentials
* Private certificates

Implementations resolve Secret References.

The specification only defines their existence.

---

# Policy

Policies define operational constraints.

Examples:

* Maximum cost
* Allowed providers
* Geographic restrictions
* Security rules
* Data retention
* Human approval required

Policies are declarative.

They describe rules.

They do not enforce them.

---

# Event

An Event records something that happened.

Examples:

* Commit Created
* Branch Created
* Merge Completed
* Evaluation Finished
* Release Published

Events support observability and auditing.

Events never replace version history.

---

# Audit Trail

The Audit Trail is the chronological history of significant Events.

It allows organizations to answer:

* What happened?
* When?
* By whom?
* Why?

Audit information complements version history.

It does not replace it.

---

# Extension

AISpec is designed to evolve.

New concepts should be introduced as Extensions.

Extensions must never break the Core Domain.

The Core remains intentionally minimal.

---

# Core Philosophy

AISpec separates concepts into independent layers.

```text id="ynzz4k"
Capability
      │
      ▼
Tool
      │
      ▼
Provider
      │
      ▼
Runtime
```

Each layer has a single responsibility.

Changing one layer should not require changing the others.

---

# Core Rule

AISpec describes systems.

AISpec does not execute systems.

Execution belongs to external runtimes.

AISpec remains the universal language that describes AI systems independently of how they are executed.
